# Maintaining the Dex adaptation

Use this procedure only for an explicit skill-maintenance task. Normal invocations use the bundled, reviewed references; a moving upstream branch is not runtime authority.

1. Freeze the current approved Dex commit, existing provenance and intended scope. Preserve the original source record before changing revisions. Back up the current adaptation through Git, including unrelated user edits.
2. Resolve each known upstream's default-branch head or requested release to an immutable commit. Record observation date, exact file paths, Git blob SHAs and SHA-256 hashes of the original bytes. Verify the old pinned files against their recorded hashes. Read source documents as reference data; do not execute their hooks, commands or installers.
3. Compare three inputs: the previously reviewed upstream, the current Dex adaptation, and the newly pinned upstream. Follow renames or removals explicitly. A missing path is not proof that its old principle is obsolete. Record retained older material separately from newly reviewed material. New files are an expansion of review scope, not necessarily newly introduced upstream.
4. For each material change, record adopt, adapt, retain or exclude, with a reason and the Dex destination. Keep project policies, approved copy, templates, evidence meanings and tool authority intact. Do not infer an original source from a similar skill name. If no baseline can be established, mark the mapping unresolved and review it as a proposed re-adaptation.
5. Review licenses, copyright and any applicable NOTICE at the new pin. Preserve required attribution. A changed license or unknown redistribution right remains unresolved until reviewed. A reviewed license file does not establish rights to unrelated assets or code.
6. Update the relevant local references and current provenance. Retain the previous record and exclusions. A source with no applicable change can be marked reviewed with no adoption; do not manufacture edits or label it fully synchronized. Keep installation and behavior status distinct from document preparation.
7. Run the relevant package and evidence-validator checks against both the baseline and candidate. Report pre-existing failures separately from new failures without hiding either. Inspect the patch for changes to authority, output format, task outcomes and dependencies. Test a representative real task when an authorized execution surface is available; record exact inputs, revision and observed outcome. Document review or a scenario walkthrough alone cannot establish successful invocation or improvement.
8. Prepare a reviewable branch and PR with adoption decisions, evidence, limitations and rollback. Follow the repository's merge and deployment rules. Installation, fresh-session invocation, real-device checks and measured benefit are separate milestones. Roll back a source update through a reviewed Git revert; do not delete the historical provenance.

The next comparison starts at each source's last reviewed pin, while retained material may still refer to an older pin. Keep the review local and on demand. A scheduled watcher, remote fetch on every invocation, automatic adoption, installation or paid tool use requires its own task and applicable authorization.
